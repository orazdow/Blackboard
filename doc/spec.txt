====== clarification =======

Initial scope:
Implement chat channels and messages first. Trello mirroring and goal tracking
are future extensions. Keep the protocol usable through ordinary GitHub issues
and comments as well as through the web client and scripts.

Channel identity:
A channel is a GitHub issue. Identify it by repository owner, repository name,
and issue number. Titles are display names and may be renamed without changing
the channel's identity.

Issue title prefixes:
Use actual Unicode emoji characters in titles, rather than literal shortcode
text. Use the speech balloon (U+1F4AC, :speech_balloon:) followed by a space for
chat channels, for example: 💬 general
Reserve the clipboard (U+1F4CB, :clipboard:) prefix for future Trello card issues.
Only issues with the chat prefix are listed as chat channels.

Channel lifecycle:
Creating a channel creates an issue with the chat prefix. Removing a channel
opens a dialog with Delete, Archive, and Cancel. Archive adds the
blackboard:archived label and hides the topic without changing open/closed
status; removing that label restores it. Delete permanently removes the GitHub
issue after the user chooses Delete in the dialog. Close/reopen is a separate
status action in the chat area and preserves message history. Open and closed
topics are both listed unless archived.
Closing a chat channel does not imply that a goal has been completed. Goal
tracking will need a separate convention when it is implemented.

Messages:
Each issue comment is one message. Use ordinary comment text, with GitHub
Markdown allowed, so messages written directly on GitHub work naturally.
The issue body is the channel description/topic, not a chat message.
Use GitHub's comment ID, author, and timestamps as message metadata. A client
must not assume a sender identity claimed in message text is authenticated.
Optional sub-identity: the exact first line _@dot declares sender "dot".
Names start with a lowercase ASCII letter, contain only lowercase letters,
digits, underscores or hyphens, and are at most 64 characters long.
sendMessage(channelId, text, { sender }) and Python's
send_message(channel_id, text, sender=...) add this line automatically.
Readers remove the marker from displayed text and preserve the GitHub author.
Comments without a marker use the GitHub author as their display identity.
Legacy hidden blackboard JSON headers/footers remain readable.
Hashtags are ordinary text initially; filtering can be added later.

Minimal client API:
listChannels({ includeClosed = false })
createChannel({ name, topic = '' })
closeChannel(channelId)
reopenChannel(channelId)
sendMessage(channelId, text)
readMessages(channelId, { cursor, limit }) -> { messages, nextCursor }

API conventions:
The client is configured with a repository and the caller's GitHub credentials.
channelId is the issue number within that repository. sendMessage returns the
created message, including its GitHub comment ID. The transport handles GitHub
pagination. readMessages returns messages in a consistent order; callers pass
back its opaque nextCursor to continue reading. Do not advance the cursor past
messages that have not been returned. Define the exact cursor format during
implementation and deduplicate received messages by comment ID.

Polling and retries:
Start with polling; realtime presence and typing indicators are out of scope.
Handle rate limits and temporary failures with backoff. A failed or timed-out
send can have an uncertain outcome: do not blindly retry and create duplicate
comments. Show an uncertain delivery state until the outcome can be checked.
Message edit/delete synchronization is out of scope for the first version.

Implementation:
Use the GitHub REST API over HTTP. Keep the protocol independent of language
and SDK so Python, Node, and browser ESM clients can implement it. Keep GitHub
transport code separate from the chat UI. A future repo-file transport can
implement the same logical operations without changing the message model.
Each participant supplies their own credentials; do not embed a shared secret
in the web application's source or built files.

=====plan=======

1. Build a small ESM JavaScript module wrapping GitHub's REST API for the
   channel and message operations described above. Use standard fetch and
   keep dependencies minimal.

2. Keep the module independent of the web UI. Accept repository configuration
   and credentials explicitly, return plain data, and expose clear errors.
   Keep DOM access, rendering, and UI state outside the module. The same module
   should work in the browser client and in Node-based scripts or agents.

3. Use the module in the web chat client to exercise and refine the API.
   Work through channel lifecycle, message sending, polling, pagination,
   deduplication, rate limits, and uncertain send outcomes before treating
   the API as stable.

4. Record the stable contract in this shared specification: operation names,
   arguments, return values, message fields, cursor behavior, and errors.
   Include small usage examples. The specification is the common reference
   for implementations in different languages.

5. Once the JavaScript API is established, implement its essential operations
   in a small Python file. Match the JavaScript operation names where practical
   and preserve the same behavior, data shapes, pagination, and error semantics.
   Keep Python dependencies minimal as well.

6. Make the Python file usable both as an executable client library for agents
   and as a readable implementation reference, with examples for reading a
   channel and sending a message. Agents may also use the JavaScript module
   directly when Node is available.

7. Maintain both implementations against the shared specification. When the
   contract changes, update the specification and both implementations together
   to prevent them from drifting apart.
